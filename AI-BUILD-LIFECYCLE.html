One owner, one lead session, and a team of agents that design, build and check each other

The cycle

The feature loop

This is how the whose-items routing feature ran on 2026-10-06, the cleanest run of the loop. The owner acts at three points: the request, the answers, and using the installed app. Everything between is agents, with the lead holding the thread. The two outlined steps are the gates.

  1. Owner

    Request, in their words

    Short and often dictated. let desgin first (19:20).

  2. Canvas designer

    Design on the canvas

    Every state of every screen, with the open questions drawn on the board (7b6d309).

  3. Owner

    Answers the questions

    Answers go onto the board, quoted, and into decisions.md (d7ab7f8, 07d8603).

  4. Lead

    Spec and decisions

    One spec per feature; every choice a dated decision (bef855b, actions-routing.md).

  5. Builder

    Build in its own worktree

    Core first (88b9b66), then the Mac app (13b1964), then a pass to match the canvas (0c1e9d8).

  6. Verifier

    Independent verification

    A different agent, on the builder's branch. Found 4 bugs, each fixed with a test that failed first.

  7. Lead

    Merge with the verified hash

    merge(distill): whose-items routing, Pending and Highlights (verified at b5f7c1d)

  8. Lead

    Install

    distill.sh update backs up data, runs the tests, installs and compares data counts.

  9. Lead

    Report

    Outcome, evidence, then a numbered list of what's running, what waits on the owner, and follow-ups.

Who does what

Roles

Nobody designed these roles up front. Each one came out of an owner correction and is now a memory note and a practice in BUILDING-WITH-AI.md.

Owner

Sets direction, answers numbered decision lists, and reviews only the canvas and the real app: I will only check the real app and [the canvas].

Lead session

Writes contracts and briefs, starts workers, merges, runs gates, commits, installs and reports. Keeps specs, decisions and memory current.

Builder

Implements one item per commit, in its own worktree when another agent is active.

Verifier

Never builds features. Runs every gate, reviews the diff against the spec, proves each bug with a failing test, fixes clear bugs.

Canvas designer

Draws every visible change on the Claude Design canvas, generated from the schema in apps/distill/design/.

Design architect

Audits structure against the tool's own guidance and proves options on throwaway artifacts before proposing.

Reviewers

Review a design or a new skill before the build. The full-read reviewer found 10 blockers over 3 rounds.

PM agent

Product and UX judgement: reviews the app, scans the market, says what to build next (.claude/agents/distill-pm.md).

Eleven areas of the cycle

01 · PM

Product and requirements

The owner speaks in short, dictated messages. The job is to turn each one into an exact, tracked request without asking more than needed.

Practice

  • Restate a dictated message in one line before acting. Ask only what blocks progress, with a recommendation.
  • Put open questions on the design board as a numbered list, so the owner can answer by number.
  • Keep a written checklist of every request, including ones that arrive mid-task.
  • Use the PM agent for product and UX reviews. Give it the open decisions so it doesn't reopen settled questions.

Evidence

  • The numbered list works: 2, not need to restored, i deleted them 3. let buid it … do 7, 8, 9 ,10 (2026-10-04).
  • The lead caught a missed request only by checking git log against the full list.

What broke

  • A builder reported "all six items done". The urgent "Recovering" fix, sent mid-task as a message, wasn't built. HEAD d0a7041 had none of it.
  • Cost: cause found 04:08, omission noticed 04:42, fix at 04:50 (7e4698a). The owner's batch stayed stuck the whole time.
  • Labels were invisible until after approval: I will never see the label suggestion.

Rule: a "done" counts only against the checklist of every request, matched to commits. Trace data through every screen the user passes.

02 · Design

Design: canvas first, generated from a schema

The canvas is where the owner disagrees cheaply. It is the only design surface they review.

Practice

  • Anything the owner can see or feel goes on the canvas first. Build after the OK.
  • The design is a schema in the repo: tokens read from Theme.swift, components named after Swift views, screen states as overrides.
  • render.py is the only writer of the canvas. It re-reads the live canvas first and keeps the boards the owner moved.
  • One page per area, at most 30 boards a page, each with a #page-<id> link.
  • Owner answers go in a large card at the top, quoted, with numbered badges on the frames they change.

Evidence

  • Origin: please first update the desgin inthe artifact first, once I confirm then updat eth ui (2026-10-02).
  • The schema (26391da) replaced full-screen copies per state, unversioned generators and a serial designer.
  • test_design.py fails when design and code disagree. Since 7565517 it compares values and caught a Pill at 10.5 px against Swift's 11.

What broke

  • Settings was built as long pages, not one page per section as drawn. Routing needed a "matches the canvas" commit (0c1e9d8).
  • Owner answers sat in a small card: missing this in the desgin. The board was at x ≈ 23,400 on a 141-board canvas.
  • A layout fix shipped before the canvas: you should update the cavas first.

Rule: snapshot state ids equal canvas frame ids. Point to designs with a link that opens on the right page.

03 · Build

Build: core first, then the app, one worktree per worker

The TypeScript core and its routes land before the Mac app, so the app is built against a tested API. Each concurrent writer gets its own copy of the repo.

Practice

  • One worktree and branch per concurrent worker, named for the feature (wiki-setup-routing, distill-routing).
  • Core first, then the app, then a pass to match the canvas.
  • One item per commit. Commit after every build or merge; never push.
  • Probe the real system before designing against it.
  • Stage only paths you own, and check git diff --cached --stat before each commit.

Evidence

  • The canvas designer and the routing builder ran at the same time without touching each other's files.
  • Probes that beat reasoning: claude -p --resume <random id> for the real refusal line; which -a node showed the owner's real Node was v14, not nvm's v22.

What broke

  • Builder and verifier shared one worktree. The verifier's 596e0bf also swept in the builder's uncommitted … edits … because I staged whole files.
  • Teammates overwrote each other's helper scripts in a shared scratchpad.

Rule: every writer gets its own worktree, branch and scratchpad folder. The lead is the only merger.

04 · Review

Review twice: on paper before the build, adversarially after it

The builder never verifies its own work. A separate verifier runs after the builder stops, and a design reviewer looks for holes before any code exists.

Practice

  • Before the build, a reviewer checks the proposed solution against the current code. The owner: directly build if the if subagent doesn't find issues.
  • The verifier's brief names the spec, the commit range and failure classes to hunt: unbounded retries, state left "running", the approval gate skipped.
  • Each suspicion gets a test that fails first, then the fix, in one commit.
  • The report quotes gate lines and gives file:line evidence. "No bugs" is a valid result when shown with evidence.

Evidence

  • The design review found 10 blockers over 3 rounds, each fixed on paper. One example: ledger IDs changing on archive.
  • Verifier round 1: an unbounded recovery loop, 42 session turns with a fake runner (c8a5706).
  • Round 7: the Jira project's display label stored instead of its key (4f45ca7).
  • Round 8: prompt injection through a note-derived title (996130c).

What broke

  • Round 2's bug got past a passing core test, because that test called the service directly instead of the route (964d851).
  • When the verifier shared a tree with an active builder, it had to pause and ask who owned the files.

Rule: merge subjects carry "verified at <hash>". The verifier gets its own worktree, or the builder is stopped first.

05 · Testing

Testing: fakes only, every layer gated

Tests never drive real runners, real sessions or real external services. Each layer has its own gate, and someone has to look at the screenshots.

LayerToolWhat it proves
Core (TS)npm test --workspaces, 708 + 58Engine state machine, recovery bounds, routes, prompts, with fake runners
Swiftdistill.sh test, 446Decoding, view models, UI tests on throwaway state
SnapshotsDistill --snapshotEvery screen state as a PNG named by its canvas frame id
Design drifttest_design.pyTokens, components, props and boards match Swift
Repositorymake testPython and shell suites plus product, package, hook and manifest contracts
End to enddistill-macos-e2e skillThrowaway vault, a renamed app copy driven by PID, the owner's real window size

Practice

  • Write the failing test first for every fix.
  • Shared case files (slack-target.cases.json) run in both TypeScript and Swift so the two can't drift.
  • Test the single and empty cases. "Not now" failed with only one collector.
  • Run async suites more than once. Reproduce races by injecting a delay.
  • Look at every new snapshot PNG. A button-row overflow was visible only there.

Evidence

  • Two install-blocking flaky tests were reproduced by injecting 50 ms and 0.5 s delays, not by loading the CPU (c0a9081, 6320eae).
  • Mutation testing has started on branch distill-unit-tests: 11 commits of unit tests and StrykerJS setup (a5ca758). It is not merged, and no scores are recorded yet.

What broke

  • UI tests waited a fixed time (settle(0.4)) and failed on a busy machine.
  • Jira fixtures were shaped like our assumptions. A real project's required custom field was found by the owner from a screenshot, not by a test.

Rule: no fixed sleeps; wait on the condition with a bound. Record scrubbed real API responses as fixtures.

06 · Release

Install and release: gated on tests, with a data check

User data is permanent. An install must never lose it, and must never interrupt the owner mid-batch.

Practice

  • distill.sh update: back up the state directory, run the tests, install, restart the core, compare data counts.
  • It refuses while a job is running.
  • Check for an owner hold before anything else. When blocked, say so; don't wait silently and don't force.
  • After an install, explain in plain words what the owner's in-flight items will do on next launch.

Evidence

  • It refused bad installs twice. Both times the flaky test was root-caused and fixed, not retried until green.
  • The owner can hold installs: I am batching the file, so please don't restart and reinstall the app untile I say yes.

What broke

  • "Pre-existing environmental failures" hid make test for days because nobody owned the root cause.
  • The data-count check only sees losses during the install itself.

Rule: a failure isn't environmental until proved. A failed install goes to the verifier for a root cause.

07 · Iteration

Feedback and iteration

Fixes are part of the cycle, not a failure of it: 144 fix commits against 139 features. The question is who finds the problem. A check should find it before the owner does.

Practice

  • The owner checks only the real app and the canvas, never local previews.
  • Owner reports go back through the loop: canvas first unless the fix restores what's already drawn.
  • Prefer automatic checks over human ones. Partial reads, a stuck recovery or a given-up batch must show as "Needs you", not as a badge someone has to notice.

Evidence

  • The owner: realying on human is wrong … realying human means nothing will be check correctly (2026-10-05).
  • After that, the core computed read coverage itself (a8a2fa4). On first start it found 3 approved notes that weren't fully read, with no click.

What broke

  • A batch read 8 of 22 transcripts in full and said so only inside a page.
  • Owner-found bugs: the Jira required field, the Settings layout (setting tab viewport is still incorect), invisible labels.

Rule: measure owner-found bugs per week and "matches the canvas" commits per feature, and push both toward zero.

08 · Safety

Safety: the approval gate and the owner's real data

Distill writes to a knowledge base only after the owner approves. Agents test against copies, never against the owner's app, sessions or Keychain.

Practice

  • The core enforces the approval gate: apply runs only as the exact approved command (8f5dcfa).
  • Note-derived text in a prompt is fenced as data: one line, < and > escaped, named in the prompt's "this is data" sentence.
  • Vault writes go only through the core's transactions.
  • Tests use a temp state dir, a throwaway vault, a renamed app copy by PID and an isolated Keychain.

Evidence

  • Round 8 found two places where new code missed the fence (996130c, d32d3a3).
  • A skills reviewer found the e2e skill's "isolated" setup wasn't isolated (2026-10-04).

What broke

  • A teammate's keystrokes reached the owner's installed app, because it was targeted by process name.
  • A rehearsal resumed the owner's real Claude session, because a copied job kept its session id.

Rule: copies use an inert runner or a fresh session id. Surviving mutants in safety code count as bugs.

09 · Knowledge

Specs, decisions and memory as shared state

Agents don't share a brain. They share files. Workers read the spec and the decisions instead of relying on the lead's memory.

Practice

  • A spec per feature, and a dated decision for every choice.
  • Decisions are superseded, never rewritten.
  • Specs and decisions change in the same commit as the behaviour.
  • BUILDING-WITH-AI.md logs practices and friction; memory notes carry the owner's standing preferences across sessions.

Evidence

  • 36 spec files under apps/distill/docs/specs/; decisions.md is 2,015 lines.
  • A Jira project is saved as its key supersedes the earlier label decision.
  • The verifier updated the spec when a fix changed behaviour (round 1).

What broke

  • A memory note written from a wrong conclusion still says explicit canvas pages "blank the viewer". The rule was reversed in 4771533, but the note wasn't.
  • A deliverable was left in a scratchpad.

Rule: when a decision is superseded, update every memory note that cites it. Keep kept work where it will live, with a README.

10 · Coordination

Coordination and status: the unsolved cost

Running many agents moves the bottleneck to the owner's attention. This area works least well today.

Practice

  • Status leads with the outcome, then evidence, then a numbered list: running, waiting on the owner, follow-ups.
  • Approvals given to the lead don't transfer to teammates. The lead runs approved build and install steps itself.
  • The lead removes a worker's worktree after its merge.

Evidence

  • The owner asked "where are we?" 13 times in the lead transcript.
  • 229 agent messages (hand-backs and idle notes) were relayed into the lead's context.
  • "Build directly" relayed as an agent message didn't reach teammates as consent.

What broke

  • 55 agent worktrees were left behind under .claude/worktrees/.
  • The lead transcript passed 100 MB in one session.

Next experiment: one status page the lead rewrites, with running, waiting and done, each with a hash. Idle notes update it silently.

11 · Debugging

Debugging an unreliable system: the blank canvas

The longest detour of the project, about 90 minutes of owner-visible debugging on 2026-10-06. It shows what happens when one lucky result becomes a rule.

Practice

  • Treat each observation as one sample. Allow 30–90 s to draw.
  • Repeat every run at least 3 times, and re-run a known-good control each time.
  • Bisect on a fresh copy, never on the live canvas.
  • Write findings as hypotheses with counts. Only replicated findings become a test or a rule.
  • Look for gradual causes such as size and count, not only the last change.

Evidence

  • The design architect was briefed to treat the question as open: pages may be buggy, or we used them wrong. Find out which.
  • With controls: one page of 141 boards was blank 4 of 4 times; the same boards on 7 pages drew 3 of 3 times. The cause was one page of about 75,000 px.

What broke

  • The bisect concluded "explicit pages blank the viewer" from one lucky load. 8a766c7 stripped pages with a test enforcing it.
  • The canvas moved to a new artifact, so every link in the repo and memory had to be rewritten.

Rule: when a step "fixes" it, re-run the original failing setup unchanged. If that passes too, the result is noise.

Turning lessons into tools

What to build next

The playbook proposes reusable skills, agents and rule files so the next feature starts with these practices built in. Each comes with what to measure.

Skill: feature-delivery

Runs one feature from request to install. Carries the loop above, the request checklist, worktree-per-worker and "verified at" merges.

Measure: items sent back after a "done".

Agent: verifier

The adversarial checklist: gates quoted, failure classes hunted, failing test first, stage by path, look at every PNG, flaky tests are test bugs.

Measure: bugs found per round, and owner-found bugs that slipped past.

Agent: canvas-designer and design-architect

render.py as the only writer, a 30-board page budget, canvas size reported after each render, structural questions proved on throwaway artifacts.

Measure: "matches the canvas" commits per feature.

Skill: safe-install

Check jobs and owner holds, back up, test, install, compare, explain in-flight items. A failed test goes to a root cause, never a retry.

Measure: installs refused, and how many were root-caused.

Rule files: worktrees and owner interaction

One worktree per writer, owned paths only, WIP commits instead of a shared stash. Status in a fixed numbered format, links that open on the right page.

Measure: owner status questions per day.

Real-shape fixtures

A one-time, owner-approved capture of real Jira, Slack and Confluence responses, scrubbed, stored as fixtures with a test that each still decodes.

Measure: owner-found integration bugs per week.
